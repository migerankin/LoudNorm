# 校准笔记

Windows Core Audio 会话 API 的两个特性决定了整个设计。两者都是在实机上实测得出的，而不是凭直觉假设 —— 因为任何一个搞错，都会让程序在无声无息中表现异常。

环境：Windows 11 build 26200，Python 3.11.15，pycaw 20251023，comtypes 1.4.16。

## 1. 会话峰值表是"音量前"的

**问题。** 会话上的 `IAudioMeterInformation::GetPeakValue` 报告的是施加 `ISimpleAudioVolume` 之前还是之后的电平？

这比看上去更重要。如果峰值表是**音量后**的，那么把一个应用调低就会让它测得的电平下降，控制器于是继续往下调 —— 一个失控的反馈环路，最终走向静音。控制器就必须把已施加的增益再除回去。

**方法。** 让某个进程播放一个幅度为 0.1（−20 dBFS）的恒定 220 Hz 正弦波，然后在三个不同的会话音量下读取同一进程的会话峰值。

**结果。**

```
  volume=1.00  peak=0.09999
  volume=0.50  peak=0.09999
  volume=0.25  peak=0.09999
```

峰值表是**音量前**的：它报告的是应用产生的内容，与会话音量无关。它几乎精确地回读了生成的幅度（0.1 对应 0.09999），证实它是 0.0–1.0 上的线性幅度，既不是 dB，也没有做归一化。

**结论。** 控制环路是开环的。测量永远不反映我们自己的输出，因此不需要反馈补偿，环路也不会振荡。

## 2. 会话音量只能衰减

`ISimpleAudioVolume::SetMasterVolume` 接受 0.0–1.0 的标量，即 −∞…0 dB。通过这个接口无法让应用比它原本的声音更响。

**结论。** `max_gain_db` 默认为 `0.0`，调高它没有任何效果 —— `GainController.volume_scalar` 无论如何都会钳到 1.0。平衡的实现是把响的应用*往下*拉到共同的目标电平。用户在主音量上补偿一次即可。

因此真正的正增益无法加进这个控制器。它现在实现在 `boost.py` 里的独立端点桥接中：Windows 把选中的应用路由到一个空闲或虚拟的渲染端点，SoundCard 采集该端点的 WASAPI 回环，浮点 DSP 施加正增益与峰值限幅，桥接再把结果渲染到收听端点。源端点和目标端点必须不同，否则桥接会采到自己的输出而形成回授。

这条路径在上述环境上做过实测：以 Realtek 为源、USB 扬声器为目标。一个低电平测试音穿过回环，共采集/渲染 48,480 帧而无流错误，处理器报告了配置的 +6.0 dB 增益。这独立于会话滑块校准（其 0.0–1.0 约束不变）验证了新增路径。

## 复现方法

两个探测脚本不属于包的一部分；它们是一次性测量。要重做"音量前/后"测试，请播放一个已知幅度的测试音，通过 PID 找到你自己的会话，并在逐级改变 `SetMasterVolume` 的同时采样 `GetPeakValue()`。端到端等价的脚本在项目历史里叫 `integration.py`，它断言：

```
measured level : -6.02 dBFS   （测试音是 -6.02）
gain applied   : -11.98 dB
volume READ    : 0.2518  <- 从 Windows 读回，不是我们自己的状态
effective out  : -18.00 dBFS  （目标 -18.0）
```

## 附带发现

pycaw 20251023 没有 `pycaw.api.audiometer` 模块；`IAudioMeterInformation` 位于 `pycaw.api.endpointvolume`。它的 COM 定义还漏掉了 `GetMeteringChannelCount`，因此只有 `GetPeakValue` 可调用。本项目只需要这一个，但从旧版 pycaw 示例抄来的代码会在这两点上都失败。
